SOCIETY MAINTENANCE TRACKER — BUILD LOG
=========================================
This file is a running, step-by-step account of what was built and why.
Each entry corresponds to one step of the Build Order in the spec
(Society_Maintenance_Tracker_Final_Build_Prompt (1).md). Decisions and
assumptions that weren't fully spelled out in the spec are recorded here
as they're made.

-----------------------------------------------------------------------
Date: 2026-08-24

What was done:
- Initialized a local git repository (branch: main). No remote configured;
  nothing will be pushed anywhere unless explicitly asked.
- Created this file (documentation.txt) and commands.txt to track the

STEP 1 — Backend scaffold + Prisma schema
-----------------------------------------------------------------------
Date: 2026-08-24

What was done:
- Scaffolded /backend as a standalone TypeScript + Fastify project
  (package.json, tsconfig with strict mode + NodeNext resolution).
- Wrote prisma/schema.prisma implementing every table from the spec's
  data model: Society, User, Complaint, ComplaintPhoto,
  ComplaintStatusHistory, Notice, NotificationLog. Every tenant-owned
  table carries society_id, matching the non-negotiable multi-tenancy
  rule. Composite indexes added on (society_id, is_overdue, priority,
  created_at) for the admin complaint list since that's the exact sort
  order the spec asks for (overdue -> priority -> age).
- Added src/config/env.ts: all required env vars (Neon URL, Better-Auth
  secret, Upstash Redis URL, R2 credentials, Resend key) validated with
  zod at boot, so a missing/malformed env var fails fast with a clear
  message instead of a confusing runtime error later.
- Added src/lib/pagination.ts: cursor helpers (encode/decode a
  base64url({createdAt, id}) cursor, buildPage()) used by every list
  endpoint — never offset/page-number, per spec.
- Added src/lib/errors.ts: a small typed AppError + Fastify error
  handler mapping it to the right HTTP status/JSON shape.
- Added src/plugins/prisma.ts and src/plugins/redis.ts: decorate the
  Fastify instance with a shared PrismaClient and ioredis connection,
  both torn down cleanly on server close.
- Wired app.ts: CORS scoped to FRONTEND_URL, global error handler,
  /healthz, and route registration under /api/v1. complaints/notices/
  dashboard/media route modules are stubbed as empty plugins for now —
  they get filled in during their own Build Order steps later in this
  log, so the app always compiles and boots as each step lands.
- Ran `npx prisma validate` and `npx prisma generate` successfully, and
  `npm run typecheck` passes clean.

Decisions / deviations from the literal spec text:
- Added two fields beyond the spec's literal table list, both required
  by the spec's own *functional* requirements: Society.invite_code
  (unique) — needed because the spec asks for "a society-selection or
  invite-code flow" for registration, and NotificationLog.idempotency_key
  (unique) — the spec explicitly says "every send attempt is idempotent
  (job carries a unique key) and logged to NotificationLog", which only
  works if that key is a real column. Both are additive, not deviations
  from the schema's intent.
- current_status on Complaint is a denormalized read column kept in sync
  by whichever request/job appends a ComplaintStatusHistory row — the
  history table is the source of truth; current_status exists purely so
  list/filter queries don't need to join+aggregate history on every read.

STEP 2 — Better-Auth + RBAC middleware
-----------------------------------------------------------------------
Date: 2026-08-24

What was done:
- src/modules/auth/auth.ts: Better-Auth instance using the Prisma
  adapter, with additionalFields (role, societyId, flatNumber, phone) on
  the user model. A `before` hook on POST /sign-up/email resolves a
  client-supplied inviteCode to a Society and injects societyId + role
  into the signup body server-side — the client can never set societyId
  or role directly on signup.
- src/modules/auth/routes.ts: bridges Fastify's raw request into a
  Web-standard Request/Response so Better-Auth's own fetch-style handler
  can serve every /api/v1/auth/* route (Better-Auth doesn't ship a
  first-party Fastify adapter, so this bridge is the standard
  integration pattern for frameworks it doesn't natively support).
- src/plugins/rbac.ts: on every request, resolves the Better-Auth
  session and decorates request.currentUser (id, role, societyId) if
  present. Exposes requireAuth and requireRole(...roles) as reusable
  preHandler hooks. Every protected route in later steps derives
  society_id exclusively from request.currentUser — never from a
  client-supplied field — which is what makes cross-tenant leakage
  impossible by construction, per the spec's Multi-Tenancy section.
- Rate limiting (@fastify/rate-limit, 20 req/min) applied to the whole
  /api/v1/auth/* group in app.ts, satisfying the spec's "rate limiting
  on /auth/* at minimum" requirement.
- src/plugins/idempotency.ts: generic Idempotency-Key header support for
  POST/PATCH (spec's API Design section) using Redis — first request
  with a given key runs normally and its 2xx response is cached for 24h;
  a replay with the same key returns the cached response instead of
  re-executing. Scoped per-tenant + per-route so keys can't collide
  across societies or endpoints.

Decisions:
- better-auth v1.7.1 (the version that actually installed) ships its
  Prisma adapter as a separate package, @better-auth/prisma-adapter, not
  a `better-auth/adapters/prisma` subpath — confirmed by reading the
  installed package's own type declarations rather than assuming.
  Adjusted the import accordingly.
- better-auth's own dependency tree requires zod ^4; this project's own
  code (env validation, later request schemas) was aligned to zod ^4 too
  rather than pinning two majors side by side, avoiding an
  --legacy-peer-deps install and keeping one zod API surface throughout
  the backend.
- Session/hook typing: used Better-Auth's documented createAuthMiddleware
  wrapper (from better-auth/api) for the sign-up hook instead of a bare
  async function, since that's what gives the callback a properly typed
  ctx.path/ctx.body — confirmed against the installed package's type
  declarations.
- Not yet tested against a live Neon database or a real browser signup
  flow (no cloud credentials exist yet in this environment) — verified
  so far only via `prisma validate`, `prisma generate`, and
  `npm run typecheck`, all passing. Full auth flow needs to be
  smoke-tested once the user has real Neon + Better-Auth env vars set.

STEP 3 — Complaints module
-----------------------------------------------------------------------
Date: 2026-08-24

What was done:
- POST /complaints (resident): create with category/description/priority.
- GET /complaints/mine (resident): own complaints, cursor-paginated.
- GET /complaints (admin): filter by category/status/priority/date range,
  sorted overdue -> priority -> age exactly as the spec requires, with
  real cursor (keyset) pagination over that 3-key compound sort.
- PATCH /complaints/:id/priority, PATCH /complaints/:id/status (writes
  an append-only ComplaintStatusHistory row + mirrors current_status),
  GET /complaints/:id/history.
- Status transitions are forward-only (Open -> InProgress -> Resolved);
  reopening a Resolved complaint is a distinct status value ("Reopened")
  on the same PATCH .../status endpoint rather than a separate route,
  since the spec's own endpoint list only names ".../status" (no
  ".../reopen") — it writes a HistoryStatus.Reopened row and resets
  current_status back to Open. This satisfies "add an explicit Reopen
  action... rather than allowing silent edits" while staying inside the
  spec's literal endpoint list.
- Every status change also enqueues a notification job (see Step 4).

Decisions:
- Compound cursor pagination problem: Prisma Client's typed query API
  can express the 3-key ORDER BY (is_overdue desc, priority desc,
  created_at asc) fine, but can't express the "<"/">" comparisons on an
  enum column needed for real keyset pagination across a 3-key cursor.
  Solved with a parameterized prisma.$queryRaw (Prisma.sql tagged
  template, never string concatenation — still honors "parameterized
  queries only") that encodes the cursor as a Postgres row-value tuple
  comparison. See backend/src/modules/complaints/adminSort.ts for the
  full reasoning on sign-flipping ASC columns so a single tuple `<`
  captures "next page" correctly.
- Any status transition clears is_overdue back to false; only the
  overdue-sweep job (Step 4) sets it true again, based on how long the
  complaint has sat in Open since the transition. Keeps "never compute
  overdue status inline on every read" true even across status changes.

STEP 4 — BullMQ (overdue sweep + notifications), in-process worker
-----------------------------------------------------------------------
Date: 2026-08-24

What was done:
- queue/connection.ts + queue/queues.ts: a dedicated ioredis connection
  for BullMQ (separate from the Fastify request-cache Redis connection),
  two queues (overdue-sweep, notifications), and typed enqueue helpers.
- queue/workers/overdueSweep.worker.ts: a repeatable job (every 5 min)
  running one set-based UPDATE across all societies at once, each
  compared against its own overdue_threshold_days via
  `now() - make_interval(days => threshold)` — not a per-complaint loop,
  and not computed inline on reads.
- queue/workers/notification.worker.ts: consumes both job types
  (complaint_status_changed, notice_posted). Every job's BullMQ jobId is
  also the NotificationLog.idempotency_key, so (a) BullMQ itself refuses
  a literal duplicate enqueue, and (b) the worker checks NotificationLog
  for an existing "sent" row before sending, covering job
  retries/redelivery. Status is logged queued -> sent/failed.
- lib/email.ts: single sendEmail(to, subject, body) wrapping Resend —
  the only file that imports the Resend SDK, so swapping providers later
  never touches business logic (spec's explicit requirement).
- server.ts starts both workers and schedules the repeatable sweep job
  right after the Fastify API starts listening, in the same process —
  per spec, since Render's free tier has no standalone worker product.

Decisions:
- Idempotency key granularity: complaint_status_changed jobs key off the
  specific ComplaintStatusHistory row id (not complaintId+status), so
  two different events that happen to land on the same status (e.g.
  Resolved -> Reopened -> ... -> Resolved again) never collide.
  notice_posted jobs key off (noticeId, residentId) since fan-out is
  exactly one job per resident per notice.
- Overdue sweep interval: spec says "runs every few minutes" without a
  number; picked 5 minutes as a reasonable default for MVP traffic.

STEP 5 — R2 pre-signed media upload
-----------------------------------------------------------------------
Date: 2026-08-24

What was done:
- lib/storage.ts: S3Client pointed at R2's S3-compatible endpoint;
  presignComplaintPhotoUpload() returns a short-lived (5 min) pre-signed
  PUT URL scoped to a key under societies/{societyId}/complaints/{id}/.

  the signed URL + the key the client must upload to.

  a sane default and documented here as an assumption.

Backend dependency note
-----------------------------------------------------------------------
Date: 2026-08-24

After the full API surface was in place, `npm audit` flagged 2 high
severity advisories in Fastify v4 (DoS via unbounded memory allocation
in sendWebStream, a Content-Type validation bypass, and an HTTP/2 DDoS
issue in its router dependency find-my-way). Since this is a brand-new
project with no legacy v4-specific code to preserve, upgraded to Fastify
v5 (+ @fastify/cors v10, @fastify/rate-limit v10, fastify-plugin v5) —
`npm audit` now reports 0 vulnerabilities. One resulting type-level fix:
Fastify v5's setErrorHandler callback types its error parameter more
strictly, so the handler in app.ts now explicitly types it as
`FastifyError | AppError`.

Date: 2026-08-24

STEP 12 — Automated code review (high effort, full diff) + fixes
-----------------------------------------------------------------------
Date: 2026-08-24

Ran an automated code review against the entire build (git diff from the
init commit to HEAD). It came back with 10 confirmed findings. All 10
were real, not false positives, and all 10 were fixed:

1. Idempotency check-and-set race (backend/src/plugins/idempotency.ts):
   the original implementation was GET-then-later-SET, so two concurrent
   requests with the same Idempotency-Key could both miss the cache and
   both run the handler — exactly the double-submit case idempotency is
   supposed to prevent. Rewrote using an atomic Redis SET...NX to claim
   the key; a second concurrent request either replays the first's
   now-ready cached response or gets a 409 asking it to retry shortly if
   the first is still mid-flight.
2. Idempotency key collision across users/resources: the key was scoped
   by societyId + route *pattern* (request.routeOptions.url, e.g.
   "/complaints/:id/status" — the same literal string for every
   complaint id), not by actor or the resolved URL. Rescoped to actor id
   + the real request.url, so different users or different resources on
   the same route can never collide.
3. AppError thrown inside the Better-Auth sign-up hook became an opaque
   500 with no body: better-call's router only special-cases its own
   APIError when turning a hook's thrown error into a response. Switched
   to throwing better-auth's own APIError (from better-auth/api) so
   "Invalid invite code" etc. actually reaches the client.
4. Overdue sweep compared against complaints.created_at, so a reopened
   complaint (which can be arbitrarily old) was immediately re-flagged
   overdue on the very next sweep tick, contradicting the sweep's own
   intent of measuring time-since-last-opened. Rewrote the comparison to
   use the timestamp of the most recent ComplaintStatusHistory row with
   status='Open' for that complaint (a correlated subquery) instead —
   correct for both a fresh complaint and a reopened one.
5. Fixing #4 surfaced a deeper bug it depended on: createComplaint never
   wrote an initial ComplaintStatusHistory row at all, so a brand-new
   complaint had no "Open" history entry (history stayed empty until the
   first status change) and would have been invisible to the sweep's new
   subquery. Fixed createComplaint to write the complaint + its first
   history row (status Open, actor = the filing resident) in one
   transaction.
6. POST /media/confirm accepted any content-type/size — those checks
   only existed in /media/presign, so a resident could skip presign
   entirely and call confirm directly with an oversized file or a
   disallowed content-type. Added the same isAllowedContentType/
   MAX_UPLOAD_BYTES checks to confirm.
7. updatePriority's response omitted `include: { photos: true }` (unlike
   getComplaintById), so the admin detail page's photo links silently
   disappeared after any priority change, since that page replaces its
   whole complaint state with the PATCH response. Added the same include.
8. Admin complaint detail page (frontend): handlePriorityChange and

-----------------------------------------------------------------------
Date: 2026-08-24

The user provided a real Neon Postgres connection string mid-session.
Wrote it to backend/.env (gitignored, never committed) alongside
generated/placeholder values for the other required env vars (a real
random BETTER_AUTH_SECRET; syntactically-valid-but-fake Upstash/R2/

testing that was previously impossible in this environment — and it
surfaced a chain of real, would-have-shipped bugs that neither
`prisma validate` nor `tsc --noEmit` nor `next build` could ever have
caught, because they only appear when the code actually talks to a real
database and a real auth flow runs start to finish.

What was found and fixed, roughly in the order they were hit running
`prisma migrate dev`, `npm run seed`, and then live curl requests against
`npm run dev`:

- ioredis crashes the whole Node process on an unhandled 'error' event
  by EventEmitter default. Neither plugins/redis.ts nor
  queue/connection.ts had an `.on('error', ...)` listener, so a
  Redis connection problem (expected right now, since only placeholder
  Upstash credentials exist) took down the entire API, not just the
  Redis-dependent parts of it. Fixed both to log and let ioredis's own
  reconnect logic keep trying instead of crashing.
- server.ts awaited scheduleOverdueSweep() (which calls BullMQ's
  queue.add(), talking to Redis) *before* app.listen(). Combined with
  ioredis's maxRetriesPerRequest: null (required for BullMQ), a call
  against unreachable Redis hangs forever instead of failing — so a
  Redis outage silently prevented the entire HTTP API from ever starting,
  including routes that never touch Redis at all (auth, most reads).
  Reordered so app.listen() only needs Fastify hooks to be registered
  first (which don't touch Redis) — the actual Redis-touching call is
  fire-and-forgotten with a .catch(), never blocking startup.
- Every /api/v1/auth/* request 404'd. Better-Auth defaults to expecting
  itself to be served from /api/auth (its `basePath` option); this app
  mounts it at /api/v1/auth (see modules/auth/routes.ts's request-bridge)
  but never told Better-Auth that, so its own internal router 404'd on
  every request before ever reaching an endpoint. Fixed by setting
  `basePath: "/api/v1/auth"` in the betterAuth() config.
- Sign-up failed with "societyId is not allowed to be set": the
  `role`/`societyId` additionalFields were declared `input: false`
  (intended to mean "the client can't set this"), but that setting makes
  Better-Auth's own endpoint schema reject the field outright — even
  when this app's own `before` hook is the one injecting it, not the
  client. Changed both to `input: true, required: false`; the actual
  security guarantee (client can never set these) comes from the hook
  unconditionally overwriting them on every /sign-up/email call, not
  from the schema.
- That fix opened a real privilege-escalation hole: with `role`/
  `societyId` now `input: true`, Better-Auth's built-in POST
  /update-user endpoint would have accepted them straight from any
  authenticated caller's request body — letting a signed-in resident set
  their own role to society_admin or hop to a different society_id
  entirely. Found by reasoning through what `input: true` actually
  exposes, then confirmed live: curled /update-user with
  {"role":"society_admin"} using a resident's session cookie and got
  "societyId is not allowed to be set" turn into a clean 403 "role and
  societyId cannot be set through this endpoint" only after adding a
  guard to the same `before` hook rejecting those two keys on every path
  except the one sign-up flow that's allowed to set them. Verified the
  guard doesn't break legitimate profile updates (flatNumber) with a
  second curl.
- Sign-up then failed with "Failed to create user" / "Argument
  passwordHash is missing": this was the deepest issue. Better-Auth does
  not store the password hash on the User row at all — it always writes
  it to a separate Account row (providerId: "credential"), supporting
  multiple linked accounts/providers per user. This app's Prisma schema,
  following the spec's literal User field list, put password_hash
  directly on User — a design that can never work with how Better-Auth
  actually persists credentials, regardless of Prisma adapter
  configuration. Used `npx @better-auth/cli generate` pointed at this
  app's real auth.ts (not guessed field names) to get an accurate
  reference schema, then hand-merged the necessary changes into
  schema.prisma: removed User.passwordHash, added User.emailVerified and
  User.updatedAt (both fields Better-Auth's internal adapter
  unconditionally includes on every user write), and added three new
  models — Session, Account, Verification — mapped to snake_case tables
  consistent with the rest of this schema. One field the CLI's reference
  didn't have (the installed better-auth 1.7.1 is newer than the
  deprecated @better-auth/cli's own internal assumptions): Account also
  needed an `issuer` column, discovered from a second live error
  ("Unknown argument `issuer`") and confirmed by reading
  better-auth/dist/api/routes/sign-up.mjs directly. This is the one
  genuine deviation from the spec's literal data model in this whole
  build, and it's a hard technical necessity, not a preference — Better-
  Auth's own sign-up/sign-in code paths reference Account.password,
  never User.passwordHash, no matter what the Prisma schema declares.
- Seed script also needed rewriting to match: it had been writing
  passwordHash directly onto User, which (a) no longer compiles against
  the new schema and (b) was never going to let seeded accounts log in
  through the real auth flow even before that, since sign-in only ever
  looks at Account. Rewrote createUser() to create the User row, then a
  matching Account row (providerId: "credential", password: hash from
  better-auth/crypto's hashPassword — the same function better-auth
  itself uses). First attempt still failed sign-in with "Invalid email
  or password" despite a verifiably-correct password hash (confirmed by
  calling verifyPassword() directly against the stored hash outside the
  HTTP flow — it returned true) — traced to sign-in.mjs filtering
  candidate Account rows by `account.issuer === credentialIssuer` where
  credentialIssuer = createLocalAccountIssuer("credential"), a synthetic
  value ("local:credential") the seed script wasn't setting. Fixed by
  importing and calling that same function (from @better-auth/core/db,
  added as an explicit dependency rather than relying on it being
  hoisted transitively) instead of hardcoding the string.
- Ran `prisma migrate reset --force` twice during this process (each
  time only against the demo/seed data seeded earlier in this same
  session, never against anything a real user would have created) to get
  a clean slate after schema changes that would otherwise have hit
  Prisma's "required column added to a table with existing rows" data-
  loss guard.
- The idempotency plugin and the dashboard summary cache both had the
  same class of bug as the boot-order issue above, just at the request
  level instead of startup: any Redis call with no timeout hangs forever
  against unreachable Redis. Confirmed live — POST /complaints with an
  Idempotency-Key header hung indefinitely until this was fixed. Added
  backend/src/lib/redisTimeout.ts (a 1.5s Promise.race wrapper) and used
  it everywhere idempotency.ts and dashboard/service.ts touch Redis; a
  timeout now degrades to "proceed without idempotency protection" /
  "compute the summary fresh without caching it" instead of hanging the
  request. Availability was judged more important than the idempotency
  guarantee during a Redis outage — a downed cache shouldn't be able to
  take down complaint creation.

After all of the above, verified live end-to-end against the real Neon
database via curl: POST /sign-up/email (new resident, invite code
resolved to the right society) — 200; POST /sign-in/email (seeded
demo account) — 200; GET /complaints/mine — 200, correctly scoped;
POST /complaints with an Idempotency-Key while Redis is unreachable —
201, degrades instead of hanging; GET /dashboard/summary as a resident —
403 (RBAC correctly blocks it); POST /update-user with
{"role":"society_admin"} as a resident — 403 (privilege-escalation guard
holds); POST /update-user with a legitimate field (flatNumber) — 200
(guard doesn't over-block); GET /notices — 200, important-first
ordering correct.

What's still not live-tested: Upstash Redis, Cloudflare R2, and Resend
all still only have placeholder credentials in this environment (no
accounts exist for them here) — so BullMQ job processing, R2 uploads,
and actual email sends remain unverified beyond code review + the
Redis-unavailable-degrades-gracefully behavior confirmed above. Postgres/
Prisma/Better-Auth/Fastify/RBAC/idempotency are now genuinely verified
against live infrastructure, not just compiled.
