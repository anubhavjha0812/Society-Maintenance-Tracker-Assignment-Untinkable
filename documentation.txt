SOCIETY MAINTENANCE TRACKER — BUILD LOG
=========================================
This file is a running, step-by-step account of what was built and why.
Each entry corresponds to one step of the Build Order in the spec
(Society_Maintenance_Tracker_Final_Build_Prompt (1).md). Decisions and
assumptions that weren't fully spelled out in the spec are recorded here
as they're made.

-----------------------------------------------------------------------
STEP 0 — Project setup
-----------------------------------------------------------------------
Date: 2026-08-24

What was done:
- Initialized a local git repository (branch: main). No remote configured;
  nothing will be pushed anywhere unless explicitly asked.
- Created this file (documentation.txt) and commands.txt to track the
  build as it happens.

Decisions:
- Package manager: npm. It's the only one available in this environment
  (no pnpm/yarn installed) and the spec doesn't mandate a specific one.
- Repo layout: two independent apps, /backend and /frontend, each with
  its own package.json — matches the spec's deliverable list exactly
  ("Full source code: /frontend (Next.js) and /backend (Fastify)").
  No npm workspaces needed since the two apps deploy to different
  platforms (Vercel / Render) and don't share code at build time.
- Design direction locked in before writing any UI code, so every screen
  stays consistent instead of drifting:
    - Type: serif display face "Fraunces" for headings/large numbers,
      paired with "Inter" for body/UI text. Deliberately not a
      sans-everywhere SaaS look.
    - Color: warm off-white background (#F7F4EF), near-black ink
      (#1B1815), one confident accent — deep clay/rust (#B5502C) — plus
      a muted forest green for resolved/positive states. No blue/purple
      gradients, no glassmorphism.
    - Surfaces: flat panels with 1px hairline borders instead of heavy
      drop shadows; shadows reserved for real overlays (modals/menus).
    - Admin lists are real tables with tabular numerals, not card grids.
    - Icons: lucide-react, monochrome, used sparingly. No emoji as UI
      icons.
- Will commit to git once per Build Order step so progress is
  checkpointed and reviewable.

Nothing runs end-to-end yet — this step is just repo + tracking setup.

STEP 1 — Backend scaffold + Prisma schema
-----------------------------------------------------------------------
Date: 2026-08-24

What was done:
- Scaffolded /backend as a standalone TypeScript + Fastify project
  (package.json, tsconfig with strict mode + NodeNext resolution).
- Wrote prisma/schema.prisma implementing every table from the spec's
  data model: Society, User, Complaint, ComplaintPhoto,
  ComplaintStatusHistory, Notice, NotificationLog. Every tenant-owned
  table carries society_id, matching the non-negotiable multi-tenancy
  rule. Composite indexes added on (society_id, is_overdue, priority,
  created_at) for the admin complaint list since that's the exact sort
  order the spec asks for (overdue -> priority -> age).
- Added src/config/env.ts: all required env vars (Neon URL, Better-Auth
  secret, Upstash Redis URL, R2 credentials, Resend key) validated with
  zod at boot, so a missing/malformed env var fails fast with a clear
  message instead of a confusing runtime error later.
- Added src/lib/pagination.ts: cursor helpers (encode/decode a
  base64url({createdAt, id}) cursor, buildPage()) used by every list
  endpoint — never offset/page-number, per spec.
- Added src/lib/errors.ts: a small typed AppError + Fastify error
  handler mapping it to the right HTTP status/JSON shape.
- Added src/plugins/prisma.ts and src/plugins/redis.ts: decorate the
  Fastify instance with a shared PrismaClient and ioredis connection,
  both torn down cleanly on server close.
- Wired app.ts: CORS scoped to FRONTEND_URL, global error handler,
  /healthz, and route registration under /api/v1. complaints/notices/
  dashboard/media route modules are stubbed as empty plugins for now —
  they get filled in during their own Build Order steps later in this
  log, so the app always compiles and boots as each step lands.
- Ran `npx prisma validate` and `npx prisma generate` successfully, and
  `npm run typecheck` passes clean.

Decisions / deviations from the literal spec text:
- Added two fields beyond the spec's literal table list, both required
  by the spec's own *functional* requirements: Society.invite_code
  (unique) — needed because the spec asks for "a society-selection or
  invite-code flow" for registration, and NotificationLog.idempotency_key
  (unique) — the spec explicitly says "every send attempt is idempotent
  (job carries a unique key) and logged to NotificationLog", which only
  works if that key is a real column. Both are additive, not deviations
  from the schema's intent.
- current_status on Complaint is a denormalized read column kept in sync
  by whichever request/job appends a ComplaintStatusHistory row — the
  history table is the source of truth; current_status exists purely so
  list/filter queries don't need to join+aggregate history on every read.

STEP 2 — Better-Auth + RBAC middleware
-----------------------------------------------------------------------
Date: 2026-08-24

What was done:
- src/modules/auth/auth.ts: Better-Auth instance using the Prisma
  adapter, with additionalFields (role, societyId, flatNumber, phone) on
  the user model. A `before` hook on POST /sign-up/email resolves a
  client-supplied inviteCode to a Society and injects societyId + role
  into the signup body server-side — the client can never set societyId
  or role directly on signup.
- src/modules/auth/routes.ts: bridges Fastify's raw request into a
  Web-standard Request/Response so Better-Auth's own fetch-style handler
  can serve every /api/v1/auth/* route (Better-Auth doesn't ship a
  first-party Fastify adapter, so this bridge is the standard
  integration pattern for frameworks it doesn't natively support).
- src/plugins/rbac.ts: on every request, resolves the Better-Auth
  session and decorates request.currentUser (id, role, societyId) if
  present. Exposes requireAuth and requireRole(...roles) as reusable
  preHandler hooks. Every protected route in later steps derives
  society_id exclusively from request.currentUser — never from a
  client-supplied field — which is what makes cross-tenant leakage
  impossible by construction, per the spec's Multi-Tenancy section.
- Rate limiting (@fastify/rate-limit, 20 req/min) applied to the whole
  /api/v1/auth/* group in app.ts, satisfying the spec's "rate limiting
  on /auth/* at minimum" requirement.
- src/plugins/idempotency.ts: generic Idempotency-Key header support for
  POST/PATCH (spec's API Design section) using Redis — first request
  with a given key runs normally and its 2xx response is cached for 24h;
  a replay with the same key returns the cached response instead of
  re-executing. Scoped per-tenant + per-route so keys can't collide
  across societies or endpoints.

Decisions:
- better-auth v1.7.1 (the version that actually installed) ships its
  Prisma adapter as a separate package, @better-auth/prisma-adapter, not
  a `better-auth/adapters/prisma` subpath — confirmed by reading the
  installed package's own type declarations rather than assuming.
  Adjusted the import accordingly.
- better-auth's own dependency tree requires zod ^4; this project's own
  code (env validation, later request schemas) was aligned to zod ^4 too
  rather than pinning two majors side by side, avoiding an
  --legacy-peer-deps install and keeping one zod API surface throughout
  the backend.
- Session/hook typing: used Better-Auth's documented createAuthMiddleware
  wrapper (from better-auth/api) for the sign-up hook instead of a bare
  async function, since that's what gives the callback a properly typed
  ctx.path/ctx.body — confirmed against the installed package's type
  declarations.
- Not yet tested against a live Neon database or a real browser signup
  flow (no cloud credentials exist yet in this environment) — verified
  so far only via `prisma validate`, `prisma generate`, and
  `npm run typecheck`, all passing. Full auth flow needs to be
  smoke-tested once the user has real Neon + Better-Auth env vars set.

STEP 3 — Complaints module
-----------------------------------------------------------------------
Date: 2026-08-24

What was done:
- POST /complaints (resident): create with category/description/priority.
- GET /complaints/mine (resident): own complaints, cursor-paginated.
- GET /complaints (admin): filter by category/status/priority/date range,
  sorted overdue -> priority -> age exactly as the spec requires, with
  real cursor (keyset) pagination over that 3-key compound sort.
- PATCH /complaints/:id/priority, PATCH /complaints/:id/status (writes
  an append-only ComplaintStatusHistory row + mirrors current_status),
  GET /complaints/:id/history.
- Status transitions are forward-only (Open -> InProgress -> Resolved);
  reopening a Resolved complaint is a distinct status value ("Reopened")
  on the same PATCH .../status endpoint rather than a separate route,
  since the spec's own endpoint list only names ".../status" (no
  ".../reopen") — it writes a HistoryStatus.Reopened row and resets
  current_status back to Open. This satisfies "add an explicit Reopen
  action... rather than allowing silent edits" while staying inside the
  spec's literal endpoint list.
- Every status change also enqueues a notification job (see Step 4).

Decisions:
- Compound cursor pagination problem: Prisma Client's typed query API
  can express the 3-key ORDER BY (is_overdue desc, priority desc,
  created_at asc) fine, but can't express the "<"/">" comparisons on an
  enum column needed for real keyset pagination across a 3-key cursor.
  Solved with a parameterized prisma.$queryRaw (Prisma.sql tagged
  template, never string concatenation — still honors "parameterized
  queries only") that encodes the cursor as a Postgres row-value tuple
  comparison. See backend/src/modules/complaints/adminSort.ts for the
  full reasoning on sign-flipping ASC columns so a single tuple `<`
  captures "next page" correctly.
- Any status transition clears is_overdue back to false; only the
  overdue-sweep job (Step 4) sets it true again, based on how long the
  complaint has sat in Open since the transition. Keeps "never compute
  overdue status inline on every read" true even across status changes.

STEP 4 — BullMQ (overdue sweep + notifications), in-process worker
-----------------------------------------------------------------------
Date: 2026-08-24

What was done:
- queue/connection.ts + queue/queues.ts: a dedicated ioredis connection
  for BullMQ (separate from the Fastify request-cache Redis connection),
  two queues (overdue-sweep, notifications), and typed enqueue helpers.
- queue/workers/overdueSweep.worker.ts: a repeatable job (every 5 min)
  running one set-based UPDATE across all societies at once, each
  compared against its own overdue_threshold_days via
  `now() - make_interval(days => threshold)` — not a per-complaint loop,
  and not computed inline on reads.
- queue/workers/notification.worker.ts: consumes both job types
  (complaint_status_changed, notice_posted). Every job's BullMQ jobId is
  also the NotificationLog.idempotency_key, so (a) BullMQ itself refuses
  a literal duplicate enqueue, and (b) the worker checks NotificationLog
  for an existing "sent" row before sending, covering job
  retries/redelivery. Status is logged queued -> sent/failed.
- lib/email.ts: single sendEmail(to, subject, body) wrapping Resend —
  the only file that imports the Resend SDK, so swapping providers later
  never touches business logic (spec's explicit requirement).
- server.ts starts both workers and schedules the repeatable sweep job
  right after the Fastify API starts listening, in the same process —
  per spec, since Render's free tier has no standalone worker product.

Decisions:
- Idempotency key granularity: complaint_status_changed jobs key off the
  specific ComplaintStatusHistory row id (not complaintId+status), so
  two different events that happen to land on the same status (e.g.
  Resolved -> Reopened -> ... -> Resolved again) never collide.
  notice_posted jobs key off (noticeId, residentId) since fan-out is
  exactly one job per resident per notice.
- Overdue sweep interval: spec says "runs every few minutes" without a
  number; picked 5 minutes as a reasonable default for MVP traffic.

STEP 5 — R2 pre-signed media upload
-----------------------------------------------------------------------
Date: 2026-08-24

What was done:
- lib/storage.ts: S3Client pointed at R2's S3-compatible endpoint;
  presignComplaintPhotoUpload() returns a short-lived (5 min) pre-signed
  PUT URL scoped to a key under societies/{societyId}/complaints/{id}/.
- POST /media/presign (resident, must own the target complaint): returns
  the signed URL + the key the client must upload to.
- POST /media/confirm: after the client PUTs directly to R2 (app server
  never sees the file bytes), this records the ComplaintPhoto row. It
  double-checks the returned key is actually prefixed with this
  resident's own society/complaint path before trusting it, so a client
  can't register a photo row against an arbitrary storage key.

Decisions:
- Allowed content types restricted to common image types
  (jpeg/png/webp/heic); max 10MB — not specified in the spec, chosen as
  a sane default and documented here as an assumption.

STEP 6 — Notices
-----------------------------------------------------------------------
Date: 2026-08-24

What was done:
- POST /notices (admin): create, optional is_important.
- GET /notices: cursor-paginated, important-pinned-first then
  newest-first. Reused the same row-value-tuple keyset pagination
  approach as the admin complaint list (notices/noticeSort.ts) — simpler

- Posting an important notice fans out one notification job per resident
  in the society onto the same BullMQ notifications queue used by
  complaint status changes — never synchronous sends in the handler.

Backend dependency note
-----------------------------------------------------------------------
Date: 2026-08-24

After the full API surface was in place, `npm audit` flagged 2 high
severity advisories in Fastify v4 (DoS via unbounded memory allocation
in sendWebStream, a Content-Type validation bypass, and an HTTP/2 DDoS
issue in its router dependency find-my-way). Since this is a brand-new
project with no legacy v4-specific code to preserve, upgraded to Fastify
v5 (+ @fastify/cors v10, @fastify/rate-limit v10, fastify-plugin v5) —
`npm audit` now reports 0 vulnerabilities. One resulting type-level fix:
Fastify v5's setErrorHandler callback types its error parameter more
strictly, so the handler in app.ts now explicitly types it as
`FastifyError | AppError`.
